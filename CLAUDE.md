# Системи глибинного навчання — лабораторні (КПІ, ПМА, 4 курс)

Репозиторій усіх чотирьох лабораторних. Студентка — Дарина. Працюю з нею українською.
Умови лаб лежать у `tasks/` (lab1.pdf … lab4.pdf, syllabus.pdf, lab2_starter.py).
Умова лаби — головне джерело правди. Якщо щось у цьому файлі суперечить PDF, правий PDF.

## Структура

```
tasks/          умови (у .gitignore, в репо не йдуть)
lab1/ … lab4/   окрема тека на кожну лабу: код .py, pyproject.toml + uv.lock, README.md, результати
```

Кожна лаба — окремий uv-проєкт у своїй теці (`uv init --python 3.12`, залежності через `uv add`,
версії зафіксовані в `uv.lock`). Команди запуску — тільки `uv run ...`.

## Незмінні правила курсу

- Python 3.12. Зерна фіксовані рівно так, як в умові. Порядок викликів генераторів — як в умові.
- Фіксовані налаштування (архітектура, lr, епохи, батч, поділ, перетворення, параметри експорту)
  не змінювати й не «покращувати». Вимушене відхилення (інша версія бібліотеки тощо) —
  тільки з поясненням у README.
- Test ніколи не використовується для вибору порога, режиму, епохи чи гіперпараметрів.
  Test обчислюється лише в команді аналізу.
- Шляхи до датасетів передаються аргументами командного рядка, не хардкодяться.
  Датасети лежать поза репо. `creditcard.csv`, набір Intel, `.onnx`-файли в git не додавати.
- Контрольні числа з умови (суми імен файлів, кількості параметрів, кількість вузлів тощо)
  перевіряти кодом і друкувати. Якщо не збігається — це помилка реалізації: зупинитися,
  знайти причину, не йти далі.
- Кожна лаба має відтворюватися однією командою на чужій машині. Числа в README беруться
  тільки з виводу команд / збережених json, нічого не вписувати руками з пам'яті.
- У README кожної лаби є розділ «Використані інструменти»: Claude Code (Anthropic) та інші
  джерела коду, якщо були.

## Як працювати над лабою

1. Прочитати PDF лаби повністю. Скласти короткий план по пунктах умови й показати Дарині.
2. Реалізувати пункт за пунктом. Після кожного пункту — запустити, звірити з контрольними
   числами, коротко сказати, що зроблено і що вийшло.
3. **Прогнози.** У лабах є пункти «запишіть прогноз до запуску» (ЛР1 дослід із помилкою,
   ЛР3 дослід із BN, ЛР4 потензорні ваги). Перед таким запуском ЗУПИНИТИСЯ і попросити
   Дарину сформулювати прогноз своїми словами. Записати його в README дослівно, з поміткою,
   що записано до запуску. Не підказувати відповідь і не правити прогноз після запуску.
4. Довгі запуски (навчання ЛР3) — спочатку короткий тестовий прогін на 1 батч / 1 епоху,
   щоб упевнитися, що все працює, і лише тоді повний. Попередити, скільки це займе.
5. README за структурою умови: таблиці, формули, відповіді на всі «поясніть».
6. Наприкінці створити `labN/DEFENSE.md` (у .gitignore). Це шпаргалка для підготовки,
   не для здачі. Формат захисту: викладач сам запускає код, читає README і код, а на парі
   показує шматок коду й просить пояснити або питає «що буде, якщо змінити параметр».
   Тому в DEFENSE.md:
   - кожна функція: що робить, чому саме так, які форми масивів на вході й виході;
   - звідки береться кожне число в README (яка функція, який файл);
   - розділ «Що буде, якщо…» для кожного важливого параметра й рішення (зерно, ε, поріг,
     правило розв'язання нічиєї, ddof, ділення на N, lr, eval/train, порядок генераторів тощо):
     що зміниться в коді, у числах і чому;
   - чернетки відповідей на всі питання з розділу «Оцінювання та захист» умови.
7. Комітити логічними кроками з нормальними повідомленнями. Не пушити без дозволу.

## Стиль коду

Код читатиме викладач і питатиме по ньому, тож він має бути простим для пояснення:
без зайвих абстракцій і «розумних» трюків, зрозумілі назви, короткі коментарі українською
там, де неочевидно ЧОМУ так зроблено (з посиланням на пункт умови). Одна функція — одна дія.

## Пастки по лабах (звіряти з PDF)

**ЛР1 (backprop, Iris).** Усе у float64. Поділ: `default_rng(0)`, класи 0,1,2, shuffle індексів
класу, перші 35 — train. Стандартизація з ddof=0 на train. Ініціалізація — НОВИЙ `default_rng(0)`,
спершу W1 (4×8, std √(2/4)), потім W2 (8×3, std √(2/11)); зсуви нулі. PyTorch Linear зберігає
вагу як (out, in) — транспонувати. Режим із навмисною помилкою (без ділення на N у градієнті
за логітами) — окремим прапорцем, за замовчуванням правильна версія.

**ЛР2 (поріг, fraud).** Використати `tasks/lab2_starter.py` як основу, навчання один раз,
аналіз — окремою командою зі збережених прогнозів. Правило s ≥ t. Кандидати: усі унікальні
оцінки validation + (+∞). Пошук через сортування й кумулятивні суми, O(n log n).
За рівної вартості — найбільший поріг. Перевірка на наборах A/B/C — незалежним прямим
перебором, не використовуючи код швидкого алгоритму. Набір C уважно розшифрувати зі
зноски в PDF. Повна таблиця кандидатів у CSV, округлення тільки для відображення.

**ЛР3 (ResNet-18, transfer).** Поділ строго за процедурою з PDF (один rng на всі класи,
сортування імен як рядків; окремий новий rng для seg_test). Звірити всі 18 клітинок
контрольної таблиці. Режими й групи AdamW (lr 3e-3 для голови/scratch, 3e-4 для layer4
в unfreeze, weight_decay 1e-4), функція `set_train_mode` з eval() для заморожених модулів.
Кількості параметрів: 11 179 590 / 3 078 / 8 396 806. Дві команди: навчання (без test)
і аналіз (перевірка SHA-256 split.csv у журналах, test на CPU один раз). Навчання може бути
на MPS/CUDA, якщо доступно. Зберегти `lab3_model.pt` за правилом вибору.

**ЛР4 (ONNX, INT8).** Модель і split.csv беруться з lab3. Контроль поділу (1200 / 11 993 084,
1502 / 33 351 444) і калібрувальної вибірки (200, сума 1 921 470, розподіл за класами).
Усі налаштування експорту, quant_pre_process, quantize_static і сесії — рівно з таблиці PDF.
Протокол затримки дослівно: сесії заздалегідь, B=1, 1 потік, 3 раунди × (20 прогрів + 100
вимірів), у вимірі лише `sess.run` між двома `perf_counter()`. Записати модель CPU, ОС
і версії бібліотек у `lab4_results.json` і README.
